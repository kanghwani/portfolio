길찾기 재설계 — 문제 · 분석 · 해결 · 결과

문제 · 우회로를 건설한 이후에도 통행량이 이동하지 않았다. 특정 경로가 포화되고 병렬 도로는 미사용 상태로 유지되었다. 최단 경로 탐색을 수백 번 반복하면 수백 대가 모두 동일한 경로를 반환받기 때문이다. 즉 기획의 핵심 상호작용이 성립하지 않는 상태였다.

분석 · 이 문제는 길찾기가 아니라 통행 배정(traffic assignment)이다. 혼잡을 반영한 휴리스틱은 설계할 수 없다 — 부하는 지금 이 경로를 배정하면서 발생하는 중이므로 순환 의존이 생긴다. 따라서 휴리스틱 기반 탐색을 배제하고 계층 분할과 상한 가지치기로 탐색량을 줄이는 방향을 택했다.

해결 · 수요를 한 대씩 순차 배정하며 확정된 경로의 타일에 부하를 적립하고, 다음 차량이 그 부하를 비용으로 인식하도록 설계했다. step = 1 + w × (부하 / 수용량), w=2.

결과 · 우회를 지시하는 분기문 없이 통행량이 병렬 도로로 분산된다. w=0이면 실패하는 회귀 테스트로 특성을 고정했고, 세이브·로드 재현성을 위해 전 구간 tie-break를 명시적으로 고정했다. 구현 후 대조 결과 교통공학의 점증 통행배정과 동일한 구조였다.

플레이테스트 기반 단일 지표 설계

문제 · 2차 빌드 플레이테스트에서 조작의 효과가 인지되지 않는다는 피드백이 나왔다. 교통 도구는 복수로 존재했으나, 설치 결과로 무엇이 개선되었는지 화면에 표시되지 않았다.

해결 · 모든 교통 도구가 공통으로 상승시키는 단일 지표를 정의했다 — 정지 없이 연속 통과한 교차로 수다. 신호등·버스 정류장·도로 확장 중 무엇을 설치해도 이 수치가 반응하며, 단계 상승 시 차체 발광 3단계와 통근 보상 가속이 적용된다.

제약 · 판정은 시뮬레이션 계층에서만 수행한다. 화면이 동시에 판정하면 진실이 두 개가 되며, 이는 이 프로젝트에서 이미 발생한 버그의 원인이었다. 신규 에셋은 사용하지 않았다.

부트캠프 1차 팀 프로젝트. 클라이언트 구현을 담당해 1개월 내 완주 후 발표했다.

담당 범위

  • 확장 구조 설계 · 무기·아이템 데이터를 ScriptableObject로 분리하고 런타임 상태를 별도 보관해, 신규 무기 추가 시 기존 코드 수정 0줄로 확장 가능한 구조를 구현(OCP)
  • 이벤트 주도 구조 · 이벤트 구독 방식으로 인벤토리·로그라이트 레벨업·통합 핫바의 UI와 시스템 로직을 분리
  • 타격감 · 히트스톱·플래시·스케일 펀치, VFX 오브젝트 풀링과 동시 상한 적용
  • 난이도 밸런싱 · 1판 클리어 시간을 약 3분에서 약 6분으로 조정

병합 충돌 회피 설계

문제 · 일시정지 상태(timeScale = 0)에서도 카메라 회전이 계속되고 마우스 커서가 해제되지 않았다.

제약 · 회전 로직이 동료가 작성한 코드 내부에 있어, 직접 수정하면 병합 충돌 위험이 있었다.

해결 · 원본 코드를 수정하지 않고 timeScale이 0일 때 회전 입력만 차단하고 커서를 해제하는 독립 컴포넌트를 별도 부착했다. 동료 코드 수정 0줄, 일시정지·레벨업·결과 화면 3개 경로에서 검증했다.
