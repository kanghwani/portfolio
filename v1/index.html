MANUAL 02

IDLE CITY

pp.03–06 · 간판 프로젝트

IDLE CITY

방치형 도시건설 시뮬레이션 · 2026.07–08 · 5인 팀 · 기획 공모전 선정작

제가 제안한 기획이 공모전에 선정되어 시작된 프로젝트입니다. 최초 기획자로서 인게임 콘텐츠를 설계했고, 구현에서는 교통 시뮬레이션 코어를 담당했습니다. 팀 커밋 604건 중 350건(58%)이 제 것이며, 코어에는 EditMode 회귀 테스트 671개를 두어 특성을 고정했습니다. 화면 계층까지 합치면 테스트는 1,204개입니다.

2.1 기획 담당

  • 도시의 하루. 출퇴근만 있던 도로에 점심·저녁 외출과 특수건물 방문을 추가해 24시간 교통 수요를 분산 배치했습니다
  • 회사 3종과 출퇴근 시간표. 사무실·물류창고·공장의 정원과 출퇴근 시각을 분리하고, 시간대를 의도적으로 겹쳐 러시아워를 데이터로 만들었습니다. 자정을 넘는 교대 근무도 판정에 포함됩니다
  • 교통 도구의 구매 대상 정의. 신호등은 무신호 교차로의 통과량 상한을 해제하고, 버스 정류장은 통근 차량 자체를 줄입니다

2.2 코어 구현

  • 길찾기 — 부하 적립 라우팅(RoutePlanner). 수백 대의 차량을 서로 다른 경로로 배분하는 통행 배정 알고리즘입니다. 앞차가 채운 부하를 뒷차가 비용으로 읽는 순차 배정 다익스트라이며, 20×20 리전 단위로 탐색을 분할합니다
  • 차량 주행. 개별 속도 시뮬레이션과 트럭 차급, 교차로 점유·연속 대기열, 정지 상태를 복구하는 워치독(재라우팅 3회·재시작 6회)을 구현했습니다
  • 시뮬레이션과 화면의 권한 분리. 위치·점유 판정을 시뮬레이션 계층으로 단일화하고 화면은 보간만 하도록 재설계했습니다(PR 5건). 차선 오프셋 프로그래매틱 검증 80/80 정확 · 차간 위반 0
  • 성능 계측 도구. 통행 배정 비용을 재는 EditMode 벤치마크를 직접 만들어, 도로망 규모별 재계획 시간을 표로 뽑고 회귀 상한을 테스트로 걸었습니다(2.4 · PR #257)
  • 경제 어뷰징 차단. 정체를 일부러 만드는 편법이 순이익이던 구조(실측: 편법 35코인 대 정상 24코인)를 무이자 정산과 장부 소각으로 뒤집고, 단언 테스트 3종으로 고정했습니다

2.3 사례 — 길찾기 재설계

문제. 우회로를 건설해도 통행량이 옮겨가지 않았습니다. 최단 경로 탐색을 수백 번 반복하면 수백 대가 전부 같은 경로를 돌려받기 때문입니다. 기획의 핵심 상호작용이 성립하지 않는 상태였습니다.

분석. 이것은 길찾기가 아니라 통행 배정(traffic assignment) 문제입니다. 혼잡을 반영하는 휴리스틱은 만들 수 없습니다 — 부하는 지금 이 경로를 배정하면서 생기는 중이므로 순환 의존이 됩니다. 그래서 휴리스틱 탐색을 버리고 계층 분할과 상한 가지치기로 탐색량을 줄이는 쪽을 택했습니다.

해결. 수요를 한 대씩 순차 배정하면서 확정된 경로의 타일에 부하를 쌓고, 다음 차량이 그 부하를 비용으로 읽게 했습니다. step = 1 + w × (부하 / 수용량), w=2.

결과. 우회를 지시하는 분기문 없이 통행량이 병렬 도로로 분산됩니다. w=0이면 실패하는 회귀 테스트로 특성을 고정했고, 세이브·로드 재현성을 위해 전 구간 tie-break를 명시했습니다. 구현 후 대조해 보니 교통공학의 점증 통행배정과 같은 구조였습니다.

2.4 성능 — 측정한 것과 아직 못 넘은 벽

통행 배정 1회(Plan)의 비용을 EditMode 벤치마크로 실측했습니다. 이 함수는 매 프레임이 아니라 도로를 지을 때만 호출되므로, 기준은 프레임 타임이 아니라 건설 클릭의 체감입니다.

차량 수에는 선형입니다. 같은 도로망에서 18대와 82대의 1대당 비용이 0.151 ms와 0.147 ms로 거의 같습니다. 부하를 쌓으며 한 대씩 배정하는 구조가 수요 증가에 대해서는 예상대로 작동한다는 뜻입니다.

도로망 크기에는 무너집니다. 도로가 175칸에서 700칸으로 4배 늘 때 1대당 비용은 27배가 됐습니다. 탐색 구역 한 변을 20으로 두고 배열 스캔 다익스트라를 쓴 선택이 그 경계를 넘는 순간 비용으로 돌아온 것입니다. 게임이 20×20에서 시작해 청크 단위로 해금되기 때문에 현재 플레이 범위에서는 드러나지 않지만, 도시가 커지면 건설 순간의 멈춤으로 나타납니다.

다음 수. 우선순위 큐로 탐색을 바꾸고, 전체 재계획 대신 변경된 구역만 다시 푸는 증분 재계획이 답이라고 보고 있습니다. 벤치마크를 테스트로 남겨 두었으므로 개선 여부는 다시 측정해서 확인합니다.

2.5 사례 — 플레이테스트 기반 단일 지표

문제. 2차 빌드 플레이테스트에서 "조작의 효과가 느껴지지 않는다"는 피드백을 받았습니다. 교통 도구는 여러 개인데, 설치 결과로 무엇이 나아졌는지 화면에 보이지 않았기 때문입니다.

해결. 모든 교통 도구가 공통으로 끌어올리는 단일 지표를 정의했습니다 — 정지 없이 연속 통과한 교차로 수입니다. 무엇을 설치해도 이 수치가 반응하고, 단계가 오르면 차체 발광 3단계와 통근 보상 가속이 적용됩니다. 판정은 시뮬레이션 계층에서만 합니다. 화면이 같이 판정하면 진실이 두 개가 되는데, 그것이 이 프로젝트에서 실제로 겪은 버그의 원인이었기 때문입니다.

Molten Arena

3인칭 웨이브 생존 로그라이트 · 2026.05–06 (1개월) · 2인 팀

3.1 담당 범위

  • 확장 구조 설계. 무기·아이템 데이터를 ScriptableObject로 분리하고 런타임 상태를 따로 보관해, 신규 무기 추가 시 기존 코드 수정 0줄로 확장되는 구조를 만들었습니다(OCP)
  • 이벤트 주도 구조. 이벤트 구독으로 인벤토리·레벨업·통합 핫바의 UI와 시스템 로직을 분리했습니다
  • 타격감. 히트스톱·플래시·스케일 펀치를 구현하고, VFX는 오브젝트 풀링과 동시 상한을 적용했습니다
  • 난이도 밸런싱. 1판 클리어 시간을 약 3분에서 약 6분으로 조정했습니다

3.2 사례 — 병합 충돌 회피 설계

문제. 일시정지(timeScale = 0) 상태에서도 카메라가 계속 돌고 마우스 커서가 풀리지 않았습니다. 회전 로직은 동료가 작성한 코드 안에 있어서, 직접 고치면 병합 충돌 위험이 있었습니다.

해결. 원본 코드를 건드리지 않고, timeScale이 0일 때 회전 입력만 차단하고 커서를 해제하는 독립 컴포넌트를 따로 붙였습니다. 동료 코드 수정 0줄. 일시정지·레벨업·결과 화면 3개 경로에서 검증했습니다.

고전에서 현대 명작까지

창세기전과 악튜러스, 파이널판타지와 드래곤퀘스트 같은 고전 명작부터 발더스 게이트 3와 메타포까지 — 장르의 기준이 된 게임들을 골라 플레이해 왔습니다. 단순히 많이 하는 것이 아니라, 이 재미가 어떤 시스템에서 나오는지 뜯어보며 플레이합니다. 지금도 새로운 게임을 계속 플레이하며 그 습관을 유지하고 있고, 그 이해가 도시 시뮬레이션과 통행 배정 설계로 이어집니다.

창세기전 시리즈악튜러스화이트데이 파이널판타지 시리즈드래곤퀘스트 시리즈스매시브라더스 삼국지 조조전랑그릿사프린세스메이커 2 스타크래프트워크래프트임진록 조선의 반격

아래는 실제 플레이 기록이 남아 있는 라이브러리 전체입니다 — 120개 타이틀 (PS4·PS5·Steam·Switch·Xbox, 2026-08 기준).

정오표 — Xbox와 Switch는 조회 API가 없어 본체 기록을 보고 직접 등재했습니다(수기 8건 · 카드에 표시). 나머지 112건은 PSN·Steam API 자동 수집입니다.

PSN·Steam API를 1회 덤프한 정적 데이터입니다. 고전 PC와 PS3 이전 세대는 자동 기록이 없습니다 — 위 계보 목록이 그 구간입니다.
