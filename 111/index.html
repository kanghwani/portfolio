1.1 이 문서 요약

게임 3개를 담았습니다. IDLE CITY는 게임 개발 부트캠프의 최종 팀 프로젝트로, 제가 낸 기획안이 팀 기획 선정을 통과해 5인이 6주간 만들었습니다. Unity로 만든 것 중 가장 깊게 판 프로젝트입니다. Molten Arena는 그 직전 부트캠프 팀 프로젝트로 2인 팀에서 1개월에 완주했습니다. PARRYWAY는 개인 작업입니다. AI를 활용해 웹 게임을 하나 만들어 올려보고 싶어서 시작했고, 착수한 날 안에 플레이 가능한 빌드까지 갔습니다.

중심은 IDLE CITY의 교통 시뮬레이션 코어입니다. 최단 경로 탐색으로는 "도로를 지으면 교통이 분산된다"는 기획 자체가 성립하지 않아서, 길찾기가 아니라 통행 배정 문제로 다시 보고 코어를 새로 설계했습니다(2.2).

각 절은 왜 그것을 문제라고 봤는지부터 시작해서 버린 선택지, 고른 이유, 그 선택의 단점 순으로 적었습니다. 틀린 진단으로 시작한 절과 만들어놓고 접은 판단(3.2)도 지우지 않고 그대로 뒀습니다.

2.1 어떤 게임인가

빈 땅에 도로와 건물을 놓으면 도시가 알아서 굴러가는 방치형 시뮬레이션입니다. 창을 전체화면으로 띄우는 대신 바탕화면 위에 얹어두고 다른 일을 하다가 가끔 눈을 주는 형태입니다. 집에 사는 사람이 아침에 회사로 출근하고 저녁에 돌아오는데, 이 통근 차량이 도로를 지나갈 때마다 수익이 들어옵니다.

이 조합을 고른 이유. 코지 게임의 수요가 눈에 띄게 커지고 있었고, 방치형은 완성된 형태가 굳어진 장르가 아니라 아직 파고들 여지가 남아 있다고 봤습니다. 바탕화면에 상주하는 형태는 그 두 가지가 만나는 자리입니다. 오래 켜두는 게임이니 보고 있지 않을 때도 도시가 스스로 굴러가야 하고, 그 요구가 뒤의 기술적 선택 대부분을 결정했습니다.

문제는 길이 막히면 수익이 멈춘다는 것입니다. 회사 3종(사무실·물류창고·공장)의 출퇴근 시각을 일부러 겹쳐 놨기 때문에 러시아워가 생기고, 플레이어는 그걸 보고 도로를 넓히거나 우회로를 내거나 신호등·버스 정류장을 삽니다.

그래서 도로를 지으면 교통이 분산된다가 이 게임의 핵심 상호작용입니다. 이것이 성립하지 않으면 도로를 짓는 행위 자체가 의미를 잃습니다. 바로 다음 절이 그 이야기입니다.

2.2 통행 배정 알고리즘 설계

PROBLEM
우회로를 지어도 통행량이 옮겨가지 않았습니다. 도로를 짓는 행위 자체가 무의미해지는 상태라, 기획의 핵심 상호작용이 성립하지 않았습니다
원인
최단 경로 탐색을 수백 번 돌리면 수백 대가 전부 같은 답을 돌려받습니다. 한 대씩 보면 전부 정답인 게 문제였습니다
CONSTRAINT
혼잡을 반영하는 휴리스틱은 만들 수 없었습니다. 부하는 지금 이 경로를 배정하면서 생기는 중이라 순환 의존이 되기 때문입니다
OPTIONS
① 차량마다 무작위 가중치를 섞는다 → 분산은 되지만 이유가 없어 플레이어가 학습할 수 없습니다
② 우회를 지시하는 규칙을 넣는다 → 도로 종류가 늘 때마다 규칙이 늘어납니다
③ 배정 자체를 순차로 바꾼다 → 채택
DECISION
수요를 한 대씩 순차로 배정하면서 확정된 경로의 타일에 부하를 쌓고, 다음 차량이 그 부하를 비용으로 읽게 했습니다. step = 1 + w × (부하 / 수용량), w=2
RESULT
우회를 지시하는 분기문 없이 통행량이 병렬 도로로 분산됩니다. w=0이면 실패하는 회귀 테스트로 특성을 고정했고, 세이브·로드 재현성을 위해 전 구간 tie-break를 명시했습니다
VERIFY
구현하고 나서 대조해 보니 교통공학의 점증 통행배정과 같은 구조였습니다. 이름을 먼저 알고 쓴 게 아니라 문제에서 나온 셈입니다
기존차량마다 최단 경로 1회
서로를 모른 채 독립 계산수백 대가 동일 경로
우회로 건설 후 통행량 이동 0
→
변경 후한 대씩 순차 배정
확정 경로 타일에 부하 적립우회 지시 분기문 0개로 분산
w=0이면 실패하는 회귀 테스트

⚠️ 분산의 정도는 아직 수치로 재지 않았습니다. 지금 제시할 수 있는 증거는 특성을 고정한 회귀 테스트까지이고, 부하 감소율 측정은 다음 작업입니다. 재지 않은 값을 적지 않으려고 여기에 밝혀둡니다.

RoutePlanner.cs  —  Assets/01_Scripts/CityFlow/Sim/ 
// ① 배정이 끝난 차량의 경로를 부하로 적립한다 (Plan)
for (int i = 0; i < demands.Count; i++) {
    var carPath = Search(grid, demands[i].SourceRoad, demands[i].SinkRoad, ...);
    if (carPath == null) continue;
    for (int p = 0; p < carPath.Count; p++)
        _load[carPath[p].y * _w + carPath[p].x] += 1f;   // 뒤차가 읽을 값
}

// ② 다음 차량은 그 부하를 비용으로 읽는다 (Search)
float capInv = cfg.RoadCapacity > 0f ? 1f / cfg.RoadCapacity : 0f;
float w      = cfg.RoutingCongestionWeight;             // w = 2
...
float step = 1f + w * _load[ni] * capInv;
float cand = _cost[cur] + step;
if (cand < _cost[ni]) { _cost[ni] = cand; _cameFrom[ni] = cur; }

우회를 지시하는 조건문이 없습니다. 비용 함수 한 줄이 바뀌었을 뿐이고 분산은 그 결과로 나옵니다. `capInv`의 0 방어는 용량 0일 때 순수 최단경로로 퇴화시키기 위한 것입니다.

이 선택의 단점. 순차 배정이라 차량 순서가 결과를 바꿉니다. 그래서 세이브·로드에서 같은 그림이 나오려면 전 구간 tie-break를 명시해야 했고, 동률일 때 낮은 인덱스를 고르도록 못 박았습니다. 병렬화도 막힙니다. 앞차의 결과가 뒷차의 입력이라 순서를 흩뜨릴 수 없기 때문입니다. 재현성을 얻고 병렬성을 포기한 셈입니다.

2.3 성능 — 잴 것이 없어서 도구부터 만들었습니다

"느린 것 같다"는 말은 나왔는데 잴 방법이 없었습니다. 프레임 타임도 맞지 않았습니다. 통행 배정은 매 프레임이 아니라 도로를 지을 때만 불리기 때문입니다. 그래서 도로망 규모를 인자로 받아 재계획 시간을 뽑는 EditMode 벤치마크를 먼저 만들었습니다 (워밍업 3회 버리고 11회 중앙값 · 회귀 상한을 테스트로 고정 · PR #257).

처음엔 차량 수를 축으로 잡았습니다. 차량이 늘면 느려질 거라 보고 차량 수만 올렸는데 1대당 비용이 안 변했습니다. 총 비용이 차량 수에 선형이라는 뜻이라 여기엔 벽이 없었습니다. 축을 도로망 크기로 바꿔 다시 재자 그제서야 벽이 나왔습니다.

차량 수에는 선형입니다. 위 두 줄이 그것입니다. 같은 도로망에서 18대와 82대의 1대당 비용이 0.15ms로 같습니다. 부하를 쌓으며 한 대씩 배정하는 구조가 수요 증가에는 버팁니다.

도로망 크기에는 무너집니다. 도로가 4배(175→700칸) 늘 때 1대당 비용은 27배가 됐습니다(차량은 82→96대라 완전한 통제 비교는 아닙니다). 탐색 구역 한 변을 20으로 두고 배열 스캔 다익스트라를 쓴 선택이 그 경계를 넘는 순간 비용으로 돌아온 것입니다. 게임이 20×20에서 시작해 청크 단위로 해금되니 지금 플레이 범위에서는 안 보이지만, 도시가 커지면 건설 순간의 멈춤으로 나타납니다.

2.4 플레이 지표 설계

2차 빌드 플레이테스트에서 조작의 효과가 느껴지지 않는다는 말이 나왔습니다. 교통 도구는 여러 갠데 설치한 결과가 화면에 없었습니다. 후보 셋을 놓고 골랐습니다.

  • 평균 통행 시간 — 버렸습니다. 신호등을 놓은 직후엔 오히려 나빠져서 클릭과 숫자가 어긋납니다
  • 도착한 차량 수 — 버렸습니다. 도로를 아무렇게나 늘려도 올라가서, 잘 놓았는지를 구분하지 못합니다
  • 정지 없이 연속 통과한 교차로 수 — 채택. 무엇을 설치하든 즉시 반응하고, 막히면 그 자리에서 끊깁니다. 플레이어가 노리는 것과 숫자가 같은 방향입니다

판정은 시뮬레이션 계층에서만 합니다. 화면이 같이 판정하면 진실이 두 개가 되는데, 그게 이 프로젝트에서 실제로 겪은 버그의 원인이었습니다.

2.5 그 외 담당

3.1 어떤 게임인가

왕이 왼쪽에서 오른쪽으로 알아서 걷습니다. 플레이어는 이동도 공격도 하지 않고 방향키 4개로 방패만 듭니다. 앞에서는 대포알이, 위에서는 폭탄이, 뒤에서는 돼지가 날아오고, 날아온 방향에 맞는 방패를 제때 들고 있으면 막힙니다.

막을 때마다 방향마다 다른 음이 납니다(↓A3 ←C4 →E4 ↑A4). 펜타토닉이라 아무렇게나 막아도 불협이 나지 않고, 잘 막으면 그게 연주가 됩니다. 막을수록 음악이 된다가 이 게임의 한 줄입니다.

100m마다 능력을 하나 고르고, 죽으면 모은 코인으로 상점에서 성장합니다. 1,000m를 걸으면 집에 도착하고 끝납니다. 제목이 약속한 목적지를 게임 안에 넣어뒀습니다.

3.2 개발 개요

CONTEXT

CONSTRAINT

3.3 방패 판정 설계

처음엔 흔한 방식대로 입력 타임스탬프와 임팩트 시각의 차이로 판정했습니다. 그런데 방향을 바꾸는 도중에도 판정이 성립해버려서, 아무 방향이나 연타하는 쪽이 유리해졌습니다.

그래서 임팩트가 일어난 순간의 방패 상태를 보도록 바꿨습니다. 방향키를 누르면 90ms 동안 그 방향에 묶이고, 활성 60ms 안에 맞으면 저스트, 140ms 안이면 패링, 계속 누르고 있으면 가드입니다. 가드는 안 죽는 대신 8m 밀립니다. 연타는 패링 창을 반씩 깎게 해서 스팸의 이득을 없앴습니다.

이 선택의 단점. 방향을 바꾸는 90ms 동안은 어떤 공격도 못 막습니다. 즉 방향 전환 자체가 비용이 되고, 동시에 두 방향이 오면 하나는 반드시 가드로 받아야 합니다. 막을 수 없는 구간을 남기는 대신 규칙이 한 문장으로 설명되는 쪽을 골랐습니다.

combat.ts  —  judgeShield() 
if (shield.dir !== attackDir)          return missed('wrong-direction');
if (shield.loweredAtMs !== null &&
    impactAtMs >= shield.loweredAtMs + cfg.lowerMs)
                                       return missed('released');
if (impactAtMs < shield.raisingUntilMs ||
    impactAtMs < shield.activeSinceMs) return missed('raising');

const activeAgeMs  = impactAtMs - shield.activeSinceMs;
const parryFreshMs = Math.min(cfg.parryFreshMs, shield.parryFreshMs);
if (activeAgeMs <= Math.min(cfg.justMs, parryFreshMs)) return judged('just');
return judged(activeAgeMs <= parryFreshMs ? 'parry' : 'guard');

입력 시각을 저장해두고 빼는 대신, 임팩트가 들어온 순간의 방패 상태 하나만 봅니다. `parryFreshMs`가 연타로 깎이는 값이고, 경계 1ms를 테스트로 고정했습니다.

3.4 속도감 튜닝

플레이해보면 계속 느렸습니다. 이동 배율을 두 배 넘게 올렸는데도 체감이 그대로였습니다.

원인은 속도가 아니라 배경이었습니다. 바닥이 가로 줄무늬 벽돌이라, 그게 가로로 흘러도 무늬가 제자리에 있는 것처럼 보입니다. 줄무늬 옷이 움직일 때 어디가 얼마나 갔는지 알기 어려운 것과 같습니다. 눈은 지나가는 세로선을 세서 속도를 읽는데, 화면에 셀 세로선이 없었습니다.

그래서 벽에 세로 배너를 4m 간격으로 세우고 배경을 3층으로 갈라 서로 다른 속도로 흘렸습니다. 이동 배율은 원래대로 되돌렸는데도 속도가 붙었습니다.

밀도도 같이 손봤습니다. 다음 공격을 임팩트 시점이 아니라 발사 시점 기준으로 예약하게 바꿔서 투사체가 날아오는 동안을 죽은 시간에서 뺐습니다. 읽을 시간(윈드업)은 그대로 뒀습니다.

체감 변화 거의 없음 · 멀미만 발생
→
변경 후벽 배너로 세로선 + 배경 3층 분리배율은 원래대로
같은 속도에서 체감 발생

4.1 어떤 게임인가

용암 지형의 아레나에서 몰려오는 적을 웨이브 단위로 버티는 3인칭 로그라이트입니다. 적을 잡으면 경험치와 아이템이 떨어지고, 레벨업 때마다 능력을 하나 골라 한 판 안에서 빌드를 완성해 갑니다. 한 판은 약 6분입니다.

2인 팀이라 역할을 나눴습니다. 저는 인벤토리·아이템 시스템, 적 AI와 조준 감지, 맵과 UI를 맡았고 동료가 플레이어 컨트롤러·카메라·무기 발사를 맡았습니다. 아이템과 적이 계속 늘어날 것을 알고 있었기 때문에 데이터를 코드에서 떼어내는 일과, 때리는 감각에 시간을 썼습니다.

4.2 인벤토리 — UI를 모르는 모델

슬롯형 인벤토리는 UI와 데이터가 엉키기 쉽습니다. 칸을 그리는 코드가 수량까지 들고 있으면 창을 하나 더 만들 때마다 규칙이 복제됩니다.

그래서 가방을 화면과 분리했습니다. InventoryModel은 TryAdd·TryRemove·HasAtLeast만 알고 UI의 존재를 모릅니다. 바뀌면 OnInventoryChanged를 한 번 쏘고, HUD·퀵슬롯·결과 화면이 각자 구독해 다시 그립니다. 화면을 추가할 때 모델은 건드리지 않습니다.

정적 데이터와 런타임 상태도 갈랐습니다. 수량·탄약은 ScriptableObject에 두지 않습니다. SO는 기준값(불변)이고, 지금 몇 개인지는 런타임 객체(ItemStack·EquippedWeapon)가 갖습니다. 섞으면 에디터에서 플레이할 때마다 에셋이 오염됩니다.

4.3 아이템 효과를 상속만으로 늘리는 구조

회복·탄약 보급처럼 효과가 계속 늘어날 것을 알고 있었습니다. 사용 코드에 if (itemType == ...)를 쌓으면 아이템이 늘 때마다 그 함수를 다시 엽니다.

ItemEffectSO를 추상 베이스로 두고 효과마다 상속하게 했습니다. 사용을 트리거하는 ItemUser는 효과의 종류를 모르고 Execute()만 부릅니다. 새 효과는 클래스 하나를 상속해 에셋으로 만들면 끝이고, 기존 코드는 수정하지 않습니다.

역할도 한 겹씩 쪼갰습니다 — WeaponSlot은 장착 상태만, HotbarSelection은 선택만, ItemUser는 트리거만 맡습니다. 셋을 묶는 접착제 역할만 ItemUser가 합니다.

4.4 적과 감지

  • 조준 감지. 화면 중앙 기준 Raycast로 대상을 판정하는 AimRaycaster를 만들어, 감지 결과가 전투와 상호작용 양쪽으로 연결되게 했습니다
  • 적 AI. NavMeshAgent 기반으로 단순 추적형(제출 필수 더미) · 근접 공격형 · 보스를 구현했습니다. 능력치는 EnemyDataSO로 빼서 프리팹을 복제하지 않고 데이터로 늘립니다
  • 맵과 내비게이션. 그레이박스 맵을 만들고 NavMesh를 베이크해, 적이 실제로 길을 찾는 상태를 팀에서 가장 먼저 세웠습니다

4.5 타격감과 부하 차단

쏘는 느낌이 밋밋했습니다. 데미지 숫자는 들어가는데 맞았다는 감각이 없었습니다. 히트스톱(맞는 순간 짧게 멈춤) · 플래시 · 스케일 펀치를 얹어 한 방의 무게를 만들었습니다.

그런데 연출을 붙이자 연출 자체가 부하가 됐습니다. 적이 몰리는 웨이브 후반에 이펙트가 동시에 수십 개 생성·파괴되면서 프레임이 흔들렸습니다. 세 겹으로 잡았습니다.

4.6 일시정지 게이트 — 병합 충돌 회피
